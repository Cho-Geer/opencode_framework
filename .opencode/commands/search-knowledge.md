Before you read or write any code, follow these steps.

> **UC7-001 Phase 0+1 HARDEN** (2026-06-18): Three-stage read-before-write
> protocol is REQUIRED for valid write-block pass in `strict`/`locked` mode.
>
> 1. **Discovery** (machine-generated by `knowledge_cache_search`):
>    `discovery.status`, `discovery.discovered_files`, `discovery.discovered_at`.
>    Tells the agent what the cache *contains* — NOT what has been read.
> 2. **Read** (agent action via `read` tool): agent opens the discovered files
>    and records which ones were actually reviewed.
> 3. **Attestation** (agent-submitted via `knowledge_cache_attest`): verified
>    read evidence cross-checked against `read_audit.jsonl` / `read_audit` DB
>    table. Status `attested` is the AUTHORITATIVE write-block gate in
>    `strict`/`locked` mode (`uc7ks-before.ts`, `compliance-gate.ts`,
>    `pre-execution-hook.sh`, `scope-before.ts`).
>
> Legacy fields `cache_sufficiency.reason` / `files_read` / `content_summary`
> produced by `knowledge_cache_search` are **DEPRECATED display-compat only** —
> they are empty / `[DEPRECATED]`-prefixed and NOT authoritative evidence.

## Step 1: Decompose the Task into Knowledge Points

Break `$ARGUMENTS` into concrete knowledge points — technologies, frameworks, APIs, or patterns you need to understand. Example:

```
Knowledge Points:
1. Redis cache patterns → caching
2. ioredis client API → caching
3. Appointment module → backend_api
```

## Step 2: Map to Domains

Read the live domain list — `project.config.json → knowledge_semantic_map.domains`.

## Step 3: Discovery Per Domain

For each domain, run the discovery chain:

1. `module_scope_declare(module: "<domain>", task_id: "<unique-id>")` — use the **same** `task_id` across all calls so that downstream compliance checks correlate.
2. `knowledge_cache_search(domain: "<domain>", task_id: "<same-id>")`.
3. From the tool response, capture the **discovery** block (NOT the legacy `cache_sufficiency.reason/files_read/content_summary` — those are `[DEPRECATED]`):
   - `discovery.status` — `sufficient` or `insufficient`.
   - `discovery.discovered_files` — cache file paths the manifest says exist for this domain (relative to `docs/official_docs/`).
   - `discovery.discovered_at` — ISO 8601 timestamp.
   - `discovery.missing_topics` — topics the cache does NOT cover (used later by `knowledge_gap_report`).

> ⚠️ `cache_sufficiency.files_read` in the response is always `[]` and
> `cache_sufficiency.reason` / `content_summary` are `[DEPRECATED]…` strings.
> Do NOT report these as evidence — they are not authoritative.

## Step 4: Read Discovered Files

For every domain where `discovery.status === "sufficient"`:

1. Open each path in `discovery.discovered_files` with the **`read` tool**
   (e.g., `read("docs/official_docs/" + path)`).
2. Skim the content for the knowledge points from Step 1.
3. Keep a running list of files you ACTUALLY reviewed — this becomes the
   `files_read` argument to `knowledge_cache_attest` in Step 5.
4. Draft a short `content_summary` (2–4 sentences) describing what you
   learned, and a `reason` explaining why these files satisfy the task.

If `discovery.status === "insufficient"` and `discovery.discovered_files` is
empty, skip to Step 6 for that domain — there is nothing to read or attest.

## Step 5: Attest Read Evidence

For every domain where you completed Step 4, submit verified read evidence:

```
knowledge_cache_attest(
  domain: "<domain>",
  task_id: "<same-id>",
  reason: "<agent-written: WHY these files are needed>",
  files_read: [<list of paths ACTUALLY read — must be ⊆ discovery.discovered_files>],
  content_summary: "<agent-written: WHAT was learned>"
)
```

The tool cross-verifies against `read_audit.jsonl` / the `read_audit` DB
table for this OpenCode session. On success it returns
`attestation.status: "attested"` — this is the ONLY status that unblocks
write operations in `strict`/`locked` mode.

### M9 self-declared insufficiency

If, after reading, you determine the cache actually does NOT cover the task
(even though `discovery.status === "sufficient"`), prefix `reason` with
`[INSUFFICIENT]`:

```
knowledge_cache_attest(
  domain: "<domain>",
  task_id: "<same-id>",
  reason: "[INSUFFICIENT] Missing NestJS v11 guard docs needed for <task>",
  files_read: [<files you did read>],
  content_summary: "<what you learned, and what is still missing>"
)
```

This writes `attestation.status: "attested"` with `cache_sufficient: false`
and BLOCKS writes until re-attested after @Knowledge-Curator fetches the
missing docs (Step 6).

## Step 6: Fetch Missing

For every domain that is insufficient (either `discovery.status ===
"insufficient"` in Step 3, or agent-declared `[INSUFFICIENT]` in Step 5):

1. `knowledge_gap_report()` — no arguments; returns all outstanding gaps.
2. Formulate a combined query for @Knowledge-Curator from
   `discovery.missing_topics` + the agent's `[INSUFFICIENT]` reason.
3. `dispatch_subagent(agent_type: "Knowledge-Curator", dag_task_id: "<unique-id>", task_description: "<query>")`.
4. `Task({ subagent_type: "Knowledge-Curator", dag_task_id: "<same-unique-id>" })`.
5. After @Knowledge-Curator returns, **re-run Steps 3–5** for the affected
   domains so the new entries appear in `discovery.discovered_files` and
   the agent can attest the newly fetched files.

> Maintenance commands (`materialize`, `jobs`, `retry-jobs`) are NOT part of
> the per-task search flow — they belong to the @Knowledge-Curator's own
> maintenance entry points and should not be invoked here.

## Step 7: Evidence Report

After completing the pipeline (re-running Steps 3–5 for insufficient
domains), **output a structured report per domain** that distinguishes
discovery from attestation:

### Evidence Report Format

```markdown
### Domain: {domain_name}

| Field | Value |
|-------|-------|
| **Discovery 状态 (Discovery Status)** | `discovery.status` — `sufficient` or `insufficient` |
| **Discovered Files** | `discovery.discovered_files` (what the cache contains — from `knowledge_cache_search`) |
| **Files Read** | `attestation.files_read` (what the agent actually read — from `knowledge_cache_attest`) |
| **Attestation 状态 (Attestation Status)** | `attestation.status` — `attested` / `pending` / `skipped` / `legacy_discovered_only` |
| **Attested At** | `attestation.attested_at` (ISO 8601) |
| **理由 (Reason)** | `attestation.reason` (agent-written WHY) |
| **读取内容概要 (Content Summary)** | `attestation.content_summary` (agent-written WHAT) |
| **Missing Topics** | `discovery.missing_topics` (empty if sufficient) |
```

### Example Output

```markdown
### Domain: opencode_framework

| Field | Value |
|-------|-------|
| **Discovery 状态** | `sufficient` |
| **Discovered Files** | `["opencode/mcp-typescript-bun/findings-summary.md", "opencode/framework/plugins.md"]` |
| **Files Read** | `["opencode/framework/plugins.md"]` |
| **Attestation 状态** | `attested` |
| **Attested At** | `2026-06-21T00:45:12.345Z` |
| **理由** | Need plugins.md to understand plugin lifecycle for new cache-after hook |
| **读取内容概要** | plugins.md covers withPluginLifecycle HOF pattern, export default requirement, input.args vs output.args semantics |
| **Missing Topics** | `[]` |
```

> **Why two file lists?** `Discovered Files` is what the manifest declares
> exists for the domain (machine-generated). `Files Read` is what the agent
> actually opened and reviewed (agent-submitted, audit-verified). Only
> `Files Read` ⊆ `Discovered Files` with `attestation.status === "attested"`
> satisfies UC7-001 Phase 1 write-block.
